# Hook audit - Phase 0 discovery

Read at Phase 0. Build every map below before scoring; edit nothing.

1. **Inventory the handlers.** Every file under `HOOKS_ROOT`. For each command hook: language and runtime (a Node file runs unchanged on Windows, macOS and Linux; a Bash file does not), the events and matchers it is wired to (from `WIRING`, read the way the notes say - a source table may encode a non-`PreToolUse` event in its matcher, and a dispatcher that runs several guards in-process is ONE wired hook whose guards are inventoried one by one), the timeout the repo's timeout source stamps, the handler form (exec `args` or shell string; exec form with the interpreter first and the plugin-root placeholder in its first argument needs no shell and no quoting and runs one process a hook on Windows, while a bare path needs the exec bit and never runs on Windows; a shell string quotes the placeholder), the shared modules it requires from its own directory, and how it reads stdin. For a mods module: each `on(...)` registration is one hook - its event, the feature function it calls and every file that function reaches, its `.catch`, the options that switch it off, and the state it owns.
2. **Read each handler end to end.** Record: what it BLOCKS (the exact shapes), what it INJECTS (`additionalContext`, plain stdout), what it REWRITES (`updatedInput`), what it DRAWS, what it RECORDS (ledger, instrument log, store); the exit codes and JSON fields it emits and at which nesting, or the mods API calls it makes; the escape its denial names; the receipts it honours and their scope and lifetime; the environment switches and options it reads; the false positives it has already fixed (they are the test cases); the incident that motivated it, quoted from the comment, the repo's instructions or its design record.
3. **Fit map against the root.** Inventory `ROOT_LAYERS` first: every directive in the house rules (always-on and path-scoped, at their deployed paths), every skill step that writes a receipt or gate file or that instructs a gated action, every agent brief's sanctioned actions and tool allowlist, and the design-record lines the notes name. Then, per hook, record its relations: `mechanizes` (the rule or skill mandate it enforces - quote it), `honours` (the receipt or gate file, who writes it, its scope and lifetime), `names` (the governing rule or the tool-loading line its denial carries), `double home` (a rule or skill still mandating in prose what the hook enforces), `contradicts` (a rule, skill step or agent brief instructing what the hook denies, or the hook denying a step a flow needs with no receipt path), `orphan` (a hook whose why lives nowhere in the root, or a rule mandate with no hook and no observable), `shadows` (an injection repeating a rule's text that is already always-on in the same prompt). Each row quotes both sides; a relation the root's empty layers cannot carry is recorded as not applicable.
4. **Wiring and parity.** Every place the repo declares or generates the hook wiring (the notes name them: a source table, a generated plugin entry and the command that regenerates it, a copy-route installer that writes `settings.json`) wires the same set with the same events, matchers and timeouts, and the `checks` that hold them together are run; the deployed `settings.json` in `DEPLOYED` matches (on a plugin route it holds no house hook entry, so one there is a leftover; on a copy route: a retired hook still wired, a hook wired without its timeout, an unquoted placeholder); the retirement list the notes name carries every hook the product stopped shipping; any doc counts agree; an env-gated instrument hook is wired off by default. Where the repo has one wiring source (a plain `hooks/hooks.json`, or a mods module's register file), parity is that source against the handlers on disk: every handler wired, every wired path present, every feature folder reached.
5. **Measure.** From `CORPUS` and `LEDGER`: per hook the block count and the block rate with its denominator (blocks per matching call, per session), the denial text length, and the per-call latency where a run recorded it (the notes say where the repo records its measured spawn time); from the tests, which failure shapes each hook replays and on which routes.
6. **Coverage map.** List the must-never and must-always actions a product of this kind owes a deterministic answer to - for one that drives coding sessions: a force-push to a protected branch, a recursive delete of an unrecoverable target, a working-tree-destroying git verb on dirty files, a credential read by value, a whole-file dump of a large source, an ungated commit or push, a write outside the project, an unapproved implementer dispatch, an edit to a protected file class (migrations, lockfiles, the central package file, the solution file), a wall-of-text answer, a turn ending on a prose question, a formatter after an edit, a green gate before 'done'. For a set that by design only observes, the map lists what it must never do itself (approve, deny or rewrite a call it was not built to, write a prompt, tool input or secret to a file, overrun its time limit) and its cover. For each: covered by a hook (which, on which routes), covered by a permission rule, or declined with a reason (measured cost too low, judgment not regex).
7. **Collision map.** Two hooks on the same event and matcher: do their jobs differ, in which order do they run (all matching command hooks run in parallel; `deny` beats `defer` beats `ask` beats `allow`; a mods module's handlers follow the order and chain the mods reference gives), what is the combined cost. Guards folded into one dispatcher are one spawn: their order is the dispatcher's, each keeps its own gates and ledger row, and a throwing guard fails open alone.
8. **Shared plugin hooks.** For every plugin in `PLUGIN_HOOKS` with a `hooks/hooks.json`: each entry's event, matcher, handler form, timeout (absent means the type-and-event default in `principles.md`, not a flat 600 - an untimed `UserPromptSubmit` entry is capped at 30 seconds and an `asyncRewake` entry runs in the background and cannot freeze a turn at all, so score only the entries that are BOTH synchronous and untimed on a hot event; the repo's timeout source cannot stamp any of them, because it owns only its own entries), what it blocks, injects or records, and the script or module it runs, read line by line like a house hook. Then its relations to the root: `collides` (an event and matcher a house hook also binds - record both jobs, the combined cost, and whether the decisions can conflict), `duplicates` (the same job as a house hook, rule or skill - a pattern warning on an edit beside the house security rule, a session-start injection beside a house one), `contradicts` (injected guidance against a house rule), `independent`. Note which of its events fire with no prompt or tool call, and whether the product's own hook switches or `allowManagedHooksOnly` would silence it.
