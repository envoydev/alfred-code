# Plugin audit - Phase 0 discovery

Read at Phase 0. Build every map below before scoring; edit nothing.

1. **The consumed set.** Parse `INSTALL_LIST`: each `name@marketplace` (or catalog server row) and its comment, the install scope rule (which flag or answer installs at project scope, which at user), the update path (does `update` pass the scope `claude plugin list --json` reports, or its own?), and the retirement path for units, beside the one for skills, agents, rules, hooks and MCPs: the list the product's update reads to uninstall a unit it stopped shipping (the notes name it, with whatever fields it keeps such as the version it retired in) - record a unit the product stopped shipping with no retirement row, since an upstream-dropped plugin then stays installed everywhere. Read every place the install list is restated (a docs table, a README count), the seeds, the graph edges into each unit, and every per-unit settings row with its verified version, from the `CATALOGS` the notes name.
2. **What each consumed unit contains.** For a plugin, from the registry's `installPath` (or `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`): the manifest (`version` present = pinned, absent = commit-SHA versioning; `dependencies`, `userConfig`, `defaultEnabled`, `settings.json`), the components (commands and skills with their descriptions and invocation flags, agents with model / tools, `hooks.json` with EVERY referenced script opened, `.mcp.json`, `.lsp.json`, `bin/`, monitors), and the source tier: official curated marketplace, the community marketplace (SHA-pinned entries, automated screening) or a third-party repository. Run `claude plugin details` for each and record the numbers. For an MCP server, from its catalog row: every route (hosted url, or the stdio runtime, package, pinned version and arguments), the credential handling (a `${VAR}` reference or a header helper, never a literal), the prerequisites, the hosts it is written to, and the package's own registry page and maintainer.
3. **The dependency closure.** Each consumed plugin's manifest `dependencies`, resolved through the registry: an auto-installed dependency is a registry row of its own, so record per dependency the plugin that declares it (`via <parent>`), the version the registry holds, its cache directory and its source tier, then read its contents exactly as step 2 reads a consumed plugin's - every hook script, MCP entry, `bin/` and monitor opened. Follow a dependency's own `dependencies` to a fixpoint. A declared dependency absent from the cache disables its parent at load (the docs: a plugin with an unresolved dependency does not load, commands included), so it is a defect of the parent; a registry dependency no installed plugin declares any more is a `claude plugin prune` proposal. For an MCP server the closure is its launch runtime and prerequisites (`npx`, `uvx`, a browser, a language runtime) and whatever the launch fetches at start.
4. **The install registry.** Per unit: scopes, versions and how many projects; version drift (the same unit at two versions across projects); leftovers (a temporary directory's entry, a project no longer on disk); units present that the product does not ship (user-added: recorded, in scope only where they duplicate a product artifact or share a server endpoint); known marketplaces and their sources; which marketplaces have auto-update on.
5. **Usage.** The repo's usage analyzer over `CORPUS`, where the notes name one, for the rollup and the per-unit INVENTORY vs USE rows (with its flag for a registry from another machine); with none, the corpus count of each unit's tool calls; per unit the `how` and the denominators. For a hooks-only plugin, grep the corpus for the plugin's own injected text and record the shape. For an LSP plugin, `LSP` tool calls plus the harness's 'Last used' line. For a unit the house artifacts cite by name with a content clause, list the citers - dependency is a form of use.
6. **Fit map against the root.** Inventory the root's four layers first: every directive in the house rules (the always-on set and the path-scoped conventions, at their deployed paths), every house skill's or command's description and trigger path, every house agent's name, model and dispatch policy, every house hook's event and job, every MCP server the house registers. Then, per child component, record its relation to the root: `cited` (a house artifact routes to it - by description, or by name with a content clause where the install guarantees it; list the citers and confirm each cited child skill, agent or tool EXISTS in the installed version), `duplicates` (the same job as a house skill, agent, hook, server or repo audit skill - found by reading both, never by name), `contradicts` (opposite guidance for the same situation as a house rule - quote both lines), `collides` (a child skill description sharing trigger phrasing with a house skill's - pairwise shared trigger terms, a pair over ~0.25 Jaccard colliding - or a child hook on an event a house guard already gates, with the order and the combined cost, or a server on the same endpoint as another registration), `overrides` (a child agent or skill whose name a project-level `.claude/agents/` or `.claude/skills/` entry shadows), or `independent`. A child agent with proactive cues ('use proactively', 'automatically') is recorded against the house dispatch policy where a house rule sets one; a child skill with side effects and no `disable-model-invocation: true` against the house side-effect gate where the house has one. When `HANDOFFS` is set, every third-party row of the `/repo-audit-system` conflict map is a fit-map row here before any other is read: confirm it by reading both sides again, never by taking the handover as proof.
