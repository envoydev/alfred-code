# Who approves a spec, a design or a plan

- The `auto_approve` value on the `kit status` line decides who approves a draft written for the user's approval - a spec, a design (one given in chat included), an implementation plan, an audit's edit plan - whatever `auto_run` says. Why: the user wanted one saved switch for approval, apart from auto-run (2026-11-16).
- `auto_approve=on`: the run approves the draft and puts no review ask. A graded draft is approved once it is at the pass score or more with no BLOCKER open; a draft with no grade - scoring off, a design given in chat - is approved as written. Say `Approved by the run (auto-approve on): <path> - <score path>`, write the same to the file's status line and to the run's ledger where it has one, and start the next step in the same turn.
- Once a spec, design or plan is approved - by the run, or by the user's yes - its next step starts: for a plan, the build. A request to prepare, write or make one - 'prepare a plan for merging', 'plan it' - is the user's word for that build, the word the `communication` rule's section 3 asks for. A question about a plan - 'how would we plan X?' - gets an answer and starts nothing. Only the user's own words against the build - 'do not build', 'stop after the plan' - hold it. The run then ends on the approved plan's path, and the close names the words that held it. A request for several plans, or for a plan as input to another piece of work, holds the build until that choice is made - an ask that auto-run may take. The build still stops where the `auto-run` skill's 'What still stops' says: a request for a plan authorises no push, merge or version bump. A hold is never written as a ruling. Why: a run approved a plan at 95 on 'prepare plan for merging'. It then stopped and asked for 'build it', and its ledger showed the stop as a ruling (the user, 2026-11-25).
- `auto_approve=off`: the draft waits for the user's yes, under auto-run too. Notify the user as soon as it is ready - a push notification where the session has a tool for one (`PushNotification` in Claude Code) - go on with work that does not depend on it, and end the turn on `Waiting for your approval: <path, or 'the design above'> - <score path, or its 'ungraded' note>`.
- A graded draft whose loop ended under the pass score waits for the user the same way under either value, its open findings listed. Under auto-run, a stall or round 3 graded does not end the loop while the ceiling is the pass score or more, unless the caller sets its own round limit: the `refining-plans` skill's loop says when it ends.
- What the user says about it is saved in `.claude/kit/settings.json` and holds in every session until it is changed: 'auto approve on' or 'approve the plans yourself' turns it on, 'I approve the plans' turns it off - in any words - do as said. Where that request's `kit status` line carries `saved: auto_approve=`, the status hook saved it; where it does not, run `node .claude/kit/settings.mjs set auto_approve on` (or `off`) yourself and say what it printed. A yes to a waiting draft approves that draft and saves nothing. Where no `kit status` line arrives, run `node .claude/kit/settings.mjs` before each approval handoff.
