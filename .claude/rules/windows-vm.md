# Everything a run makes in the Windows VM lives under C:\Claude-MacOs

- A run that works in a Windows VM from macOS - `prlctl exec`, a remote shell, a test or a gate leg - keeps every file it makes or copies there under `C:\Claude-MacOs`, on the guest's own disk and not on the host shared folder. Why: one place for all the data Claude uses in the VM, so it is found, reused and removed in one spot (the user's request, 2026-11-20).
- Each run works in `C:\Claude-MacOs\<repo>\<run>\`: `<repo>` is the name of the repo folder the session runs in, and `<run>` a short id of 8 characters or fewer that the run picks and records, since Windows paths stop at 260 characters. Create the folders where they are missing.
- Its clones, bundles, logs, outputs and scratch files go there, and so do its project dependencies.
- What later runs reuse goes in `C:\Claude-MacOs\<repo>\shared\`: a clone kept across runs, a package cache (`npm_config_cache`, `NUGET_PACKAGES`). The `cleanup` rule leaves it.
- Set `TEMP` and `TMP` to `<run>\tmp` in the environment of the run's own commands only - never with `setx` or in the registry. Why: the VM's own temp folder is cleaned by no one.
- The host shared folder (`\\Mac\<share>`) only carries files between the Mac and the VM. Put what the run passes through it in `\\Mac\<share>\Claude-MacOs\<repo>\<run>\`, and copy a file into the run's folder before using it. Run nothing from the share: symlinks and `npm` installs fail or crawl on it.
- A tool's own installer writes where it must - `Program Files`, a global `npm` folder. Install nothing the task does not need, and name each install in the close.
- A script committed in a repo before 2026-11-20 that names another folder in the VM keeps it until that repo moves it; the close names the folder it used. A script the run writes follows this rule.
- At the end the `cleanup` rule removes the run's folder and its folder on the share, each by its recorded path, unless it holds work or an output the user asked to keep. It never removes `C:\Claude-MacOs`, a `<repo>` or `shared` folder, or another run's folder.

## The user can see the run

- A run that uses the VM shows what it does, on the Mac and inside Windows. Why: a run that stalled in the VM looked the same as one at work, and the user could not tell whether it still ran (the user's request, 2026-11-25).
- Start the VM with its window on the Mac, never headless: open Parallels Desktop first (`open -a "Parallels Desktop"`), and set the VM's startup view to `window` (`prlctl set <vm> --startup-view window`) where `prlctl list -i <vm>` shows another. The close names the old value. For a VM that already runs, open its bundle - `open "<the Home path from prlctl list -i>"` - since the startup view acts only at the next start.
- A `prlctl exec` command runs as SYSTEM in a session with no desktop, so no window it opens is seen. So each step writes a line to `<run>\run.log` when it starts and when it ends. The start line carries the time, the step and its process id. The end line carries the time and the exit code.
- Send a command's output to the Mac and to the log at once, in UTF-8: `2>&1 | ForEach-Object { $_; Add-Content <log> $_ -Encoding utf8 }`. Wrap a committed script's call this way, and leave the script as it is.
- Show the log live in the signed-in user's session, in a PowerShell window titled `Claude <repo> <run>` that runs `Get-Content <log> -Wait -Encoding utf8`. Find the user with `(Get-CimInstance Win32_ComputerSystem).UserName`. Register the task `\Claude-MacOs\<repo>-<run>` with `Register-ScheduledTask` and a principal for that user with `-LogonType Interactive`, then start it with `Start-ScheduledTask`. Send the script through `-EncodedCommand`, since `prlctl exec` drops quotes. Record the task's name.
- Check once that the window shows: wait about five seconds, run `prlctl capture <vm> --file <a scratchpad path>`, and read the picture. A locked session shows the lock screen there. Where no user is signed in, the session is locked or the window does not show, say so in chat at once and go on with the run.
- In chat, say when the VM starts, when each step starts, and when the run ends, with the path of `run.log`. Where an exec stops answering, run `prlctl status <vm>`: a VM whose window was closed can be suspended, and the chat says so.
- When the run ends, stop the window with `Stop-ScheduledTask`, then delete the task with `Unregister-ScheduledTask`, both by its recorded name. Do this before the `cleanup` rule removes the run's folder, since the window holds `run.log` open. After a failed run, the window, `run.log` and the VM stay for the user to read, and the close names them with the commands that end them.
