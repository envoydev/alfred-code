The API is about to go behind the company gateway. The gateway signs people in and passes on who they are in the same `X-Demo-User` and `X-Demo-Role` headers we use today - but anyone who can reach the API directly can send those headers themselves. From now on the API must only believe them when the gateway vouches for them.

- Add a setting `Auth:GatewayKey`. When it is set to a non-empty value, the identity headers are trusted only if the request also carries an `X-Demo-Signature` header whose value is the HMAC-SHA256 of the `X-Demo-User` value, a line feed (`\n`), and the `X-Demo-Role` value, keyed with the setting's value. The text and the key are both UTF-8, the header values are taken exactly as they arrive, and the signature is written as hex - accept upper or lower case. Compare it in constant time.
- A request whose signature is missing or doesn't match is treated as not signed in at all: the same 401, with the same error body, that a request without any identity headers gets today. It is never let through, and it never gets a 403 either.
- A correctly signed request goes through exactly as it does today, role checks included: a signed `member` is still refused staff work, and an unknown role is still refused the way it is today.
- When `Auth:GatewayKey` is absent or empty, nothing changes: the headers are trusted without a signature, and an `X-Demo-Signature` header is ignored. Local development and the test suite run that way and must keep working.
