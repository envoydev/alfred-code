## What this settles for Tasks 3-5

The installer never needs to run `claude plugin update <old-name>` or parse console output to detect
a migration - it reads `enabledPlugins` (user and project) and `installed_plugins.json` directly, and
those only carry the new names after a session has actually started at least once. A project's
`Agent(claude-stack:<seat>)` deny lines can stay as they are; no rewrite pass is needed there. A
fresh install must never hardcode `claude-stack@claude-stack` (S5) - it has to resolve the plugin
through whatever key `claude plugin marketplace list --json` (S7) reports for this install.

`claude plugin list --json` is richer than it first looked (S9): a `noteDetails: [{type:
"plugin-renamed", related}]` entry appears on the OLD id as soon as the marketplace catalog is
refreshed, before any session runs - the installer can check for a pending rename with one read-only
call instead of forcing a session. Materializing the renamed plugin's own cache directory (S3, S8)
needs an explicit `claude plugin update <new-id>@<key>` call - a session migrates `enabledPlugins`
but does not itself write a populated cache dir for the new name; the update call does, even though
it reports 'already at the latest version'. Both findings hold for a subdirectory source and a
root (`./`) source alike - the real repo's shape changes nothing about either behavior.

## What S10-S15 settle for the fold-in decision

**The fold-in as speced (`renames: { "claude-stack-hooks": null }`) produces at least one, and
measured up to three consecutive, sessions with NO guard hooks at all** for any project already
running the 1.x two-plugin install - S11's central finding, reproduced independently twice. The cause
is not the `null` value (S10 shows it validates fine, and S13 shows the plain 'absent from renames'
alternative breaks identically) - it is the CLI's migration writing `enabledPlugins` for the new,
folded id without actually installing it (`installed_plugins.json` never gets a row, `claude plugin
update <new-id>` reports `not_installed`), and that broken state does not self-heal by running more
sessions. The only fix found is explicit: `claude plugin install <new-id>@<key> -s <scope> -y` right
after the rename is detected, before relying on the plugin's hooks for anything. A fresh install
(S14) and a project with no prior v1 state are unaffected - the break is migration-specific. S15
confirms plugin hooks and project-`settings.json` hooks both fire unconditionally in this toy, so the
real installer's migration step must issue that repair call itself (detected via `plugin list --json`'s
`noteDetails`/`errorDetails`, per S9) rather than trust a session to complete the move.

**The root cause is broader than the hooks fold: any rename of a root-sourced plugin (this repo's own
