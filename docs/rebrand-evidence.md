# Rebrand spike evidence - what Claude Code does with a renamed plugin

Measured 2026-09-24 against Claude Code 2.1.281 (macOS). The marketplace is a local git repo served
over smart HTTP (`git http-backend`); sessions run against an Anthropic Messages API stub answering
'ok' - no model billed. `<run>` replaces every absolute scratch path below. v1 registers marketplace
`claude-stack` with plugins `claude-stack` (one agent `seat-a`, one skill) and `claude-stack-hooks`
(empty); v2 pushes the same repo with `name: envoydev`, plugins renamed to `alfred-code` /
`alfred-code-hooks`, and a top-level `renames` map.

| Spike | Command | Verbatim result (trimmed) | Conclusion |
|---|---|---|---|
| S1 | `claude plugin marketplace update claude-stack`<br>then `cd <run>/project && claude -p 'say ok' --max-turns 1` | Before the session, user and project `enabledPlugins` still read `claude-stack@claude-stack`. After the one session, with no other command run:<br>`user settings.json: "enabledPlugins": {"alfred-code@claude-stack": true, "alfred-code-hooks@claude-stack": true}`<br>`project settings.json: "enabledPlugins": {"alfred-code@claude-stack": true}`<br>No rename text appeared in stdout or stderr, plain or with `--debug` - the settings-file rewrite is the only observable signal in headless mode. | Startup migration happens. `enabledPlugins` in user AND project settings is rewritten to the new names at the next session start, not at `marketplace update` time, and silently in `-p` mode. The plan's premise holds - proceed. |
| S2 | From a fresh v1 install (marketplace never updated, no session run yet): `claude plugin update claude-stack@claude-stack --json` | `{"command":"update","outcome":"failed","plugin":"claude-stack@claude-stack","message":"Plugin \"claude-stack\" not found","failureCode":"not_found"}`<br>The local marketplace clone was silently refreshed to the v2 commit as a side effect (`git log` in `config/plugins/marketplaces/claude-stack` shows the v2 commit) even though the command failed. | The CLI does not follow `renames` for a literal old plugin id passed on the command line - it refreshes the catalog first, then fails to resolve `claude-stack` against the now-renamed list. Only a session start (S1) is rename-aware. |
| S3 | Inspect `<run>/config/plugins/cache/claude-stack/` and `installed_plugins.json` after S1's session. The plugin's files are served straight from `config/plugins/marketplaces/claude-stack/plugins/claude-stack/...` - the marketplace's own clone, already at the v2 commit. | For a plugin whose `source` sits inside the marketplace repo, the CLI never materializes the renamed cache path; it reads from the marketplace clone and orphans the old versioned cache dirs instead. The recorded `installPath` for such a plugin is nominal, not a promise the directory exists. |
| S4 | `claude plugin list --json` (same env as S1, after its session) | `[{"id":"alfred-code-hooks@claude-stack","version":"2.0.0","scope":"user",...},`<br>`{"id":"alfred-code@claude-stack","version":"2.0.0","scope":"project",...}]` | Row ids are `<new plugin name>@<unchanged marketplace key>`. The marketplace key never moves, matching what was already established for the marketplace's own rename. |
| S5 | Fresh config dir, never touched by v1: `claude plugin marketplace add http://127.0.0.1:<port>/remote.git` (v2 source), then `claude plugin install claude-stack@claude-stack -s user -y --json` | `add` registers key `envoydev` (the v2 manifest's own `name`, not `claude-stack`).<br>`install`: `{"command":"install","outcome":"failed","plugin":"claude-stack@claude-stack","message":"Plugin \"claude-stack\" not found in marketplace \"claude-stack\"...","failureCode":"not_found"}` | Confirms D1's premise. A fresh project using the old hardcoded `claude-stack@claude-stack` spec fails outright: the marketplace key `claude-stack` and the plugin name `claude-stack` both exist only for an install that predates the rename. |

Then two fresh sessions from the same post-rename state: one with no deny, one with deny rewritten to `Agent(alfred-code:seat-a)`. | No deny: `alfred-code:seat-a` IS listed among 'Available agent types for the Agent tool' in the request body.<br>Deny `Agent(claude-stack:seat-a)` (old spelling, S1's actual state): 0 occurrences of `seat-a` in the listing.<br>Deny `Agent(alfred-code:seat-a)` (new spelling, control): 0 occurrences of `seat-a` in the listing. | Both the pre-rename and post-rename deny spellings block the renamed agent equally. Row shape is `{name, source, url, installLocation}`, matching `known_marketplaces.json`'s own per-key shape - Task 5's key resolver can read either. |

## What this settles for Tasks 3-5

The installer never needs to run `claude plugin update <old-name>` or parse console output to detect
a migration - it reads `enabledPlugins` (user and project) and `installed_plugins.json` directly, and
those only carry the new names after a session has actually started at least once. A project's
`Agent(claude-stack:<seat>)` deny lines can stay as they are; no rewrite pass is needed there. A
fresh install must never hardcode `claude-stack@claude-stack` (S5) - it has to resolve the plugin
through whatever key `claude plugin marketplace list --json` (S7) reports for this install.
