Alfred Code.
The house rules, the tools and the checks, set up before Claude starts work.

Alfred Code sets Claude Code up before it starts work in your project. It reads the project, picks what the project needs from a catalog of skills, agents, rules, hooks and plugins, and installs it. From then on Claude follows your conventions without being asked, works in gated steps you approve, and a risky move is stopped before it runs. Each tab below covers one part: start with Overview and How it works, then open the catalog tabs to look anything up.

The idea

Claude Code starts every project cold: it does not know your conventions, it can run a command that destroys work, and left alone it plans, builds and reviews in one breath. Alfred Code closes that gap before the first message. The yardstick every part is judged by: Sonnet at high effort, run through this stack, does better work than Opus at high effort without it - pre-digested context, deterministic scripts and hooks doing the navigation and the checking, and small gated steps instead of broad reads.

Conventions

The house style loads by itself

Open a .cs, .ts or template file and the matching rule attaches its skill on its own. Claude writes the code the way the stack expects - no prompt needed.

Guards

Mistakes are stopped, not warned about

A force-push to main, a reset --hard over uncommitted work, a secret printed, an unreviewed commit, a write into another repo - each is blocked before it runs. When a block needs your decision, it ends in one question.

Gated flows

Work runs in steps you approve

/task-solve designs, checks the plan, waits for your approval, builds test-first, reviews and closes. /issue-diagnoser proves a cause before anything is fixed.

Agents

Specialists plan, build and check

Each stack has three seats - a designer plans, implementers build in parallel after you approve, a verifier reviews. Work across backend and frontend ends with a read-only integration review.

What one install lays down

The installer picks from the catalog by what it finds in the project; /alfred-code:configure adds or removes any row later.

Quick start

Node 26 (22.12 is the oldest that still runs), Claude Code 2.1.296 or newer, the claude CLI and git.

# 1. in your project folder
claude plugin marketplace add anthropics/claude-plugins-official
claude plugin marketplace add envoydev/plugins-marketplaces
claude plugin install alfred-code@envoydev --scope local

# 2. inside Claude Code: scan, recommend, install what you keep
/alfred-code:init

# 3. restart Claude Code, then the one-time finish
/alfred-code:init

How it works

Six pictures, from the install to how one domain team runs. A stop tag marks a step that waits for you: one question with a recommended option. Under auto-run each stop takes that option, and nothing outward (a push, a merge, a deploy) happens unasked.

1 · Install, then keep it current

One command per step; the installer is the only route that writes, on every OS.

  1. pluginInstall the core pluginclaude plugin install alfred-code@envoydev - the hooks and the nine commands
  2. scan/alfred-code:initreads the project, finds its stacks, recommends a set with the reason for each rowstop - you pick
  3. installThe installer writesskills and rules into .alfred/stack/, a link per skill, the settings, the install stamp
  4. finishRestart, /alfred-code:init againthe language servers, the status line, the first project docs
  5. workWork as usualrules, guards and seats run on their own

/alfred-code:statusread-only: what is installed, whether it runs, what gets used
/alfred-code:uninstallremoves exactly what the stamp recorded, nothing of yours

3 · One task through /task-solve

The single-chat flow for a feature or a fix. The size is stated first and decides which steps run: a trivial change skips the plan, a cross-stack one is pointed to /task-solve-cross.

  1. sizeOne Size: linetrivial, small, standard or cross - never below the floor the spec check prints
  2. 1 designClarify, then designthe readings of the ask, one question at a time; the plan folder is writtenstop - review
  3. 2 gateCheck the plana risk review names the traps the stack will hit, and stamps the plan
  4. 3 approveApprove and pick the modebuild in this session, or fan out to the stack's seatsstop - approve
  5. 4 buildBuild test-firsttask by task, each ticked in the plan's status filestop - reviewer
  6. 5 reviewConformancein-session review or the stack's verifier; each fix re-reviewed
  7. 6 closeThe done gatebuild and tests run after the last edit, output quoted; anything pending goes into the close questionstop - close
The plan folder holds the plan, a status.json and a scoring.json, written only by the plan-status script. A fresh session resumes from the folder alone. With scoring on, a fresh grader scores the plan before you see it.

4 · A failure through /issue-diagnoser

Any evidence - a stack trace, a red CI run, written repro steps, a bare report. The cause is proven before anything is fixed.

  1. 1 triageName the evidence tiertier 1 a trace, down to tier 4 a bare report; the tier is carried as the confidence label
  2. 2 gatherReproduce and collectin this session, or one evidence-gatherer seat per source
  3. 3 root causeThe root-cause loopfail on demand, walk back from the throw, one hypothesis per changestop - the fork
4 · the fork - one question, three outcomes
Plan the fix as tasksrecommended when the cause is proven: task cards for /task-solve
Write a reporta standalone document, when the fix is someone else's or not now
Add log points and re-runrecommended when the cause is unproven: the next occurrence arrives a tier higher

Features

What the stack does for you once it is installed, grouped by the job it does.

Safety

Guards

Blocked before it runs

  • a force-push to main, master or develop
  • git reset --hard, clean -f or rm over work that has no undo
  • a large commit that was never reviewed
  • loosening a lint or test config so a failing check passes
  • reading a whole 2,000-line file to find one method - symbol search instead
Secrets

A credential is read for its presence

cat .env shows the keys with the values masked. The project's secrets file under .alfred/ cannot be read, and a printed value is masked; a command that needs one gets it in its environment.

Boundaries

One session, one project

A write into another repository is blocked and becomes a task card for that repo. In a workspace, a session may write anywhere inside it; past it, the main session asks and a seat is refused.

Approval

Nothing builds unapproved

An implementer seat is dispatched only with its plan's approval stamp, written when your decision lands. A guard's own question - a discard, a write outside the project - is always yours, even under auto-run.

Modes - typed once, on until off

Type the command alone on a line with on or off. A mode stays on in this session and every new one in the same checkout; each prompt shows the modes that are on.

auto-run

/alfred-code:mode:auto-run on

Each question takes its recommended option, so a run goes on while you are away. No push, merge, deploy or publish happens unasked. /mode-auto-run <request> runs one request this way.

scoring

/alfred-code:mode:scoring on

A fresh grader scores plans and root-cause verdicts before they are released to you. on 80 also sets the pass level (60 to 100).

auto-compact

/alfred-code:mode:auto-compact on

Stops the fresh-session question: a long session compacts and goes on.

Context that is ready, not searched for

Rules

Conventions by file type

Six always-on basics (interaction, quality gates, security, preferences, navigation, the docs root) and twelve path rules that attach the right skill on the first touch of a matching file.

Docs memory

The project's own docs

The captures write the architecture, code style, run book and related-project docs under .alfred/docs/; a session starts with their start block instead of reading the code broadly.

Preferences

What you want, in your words

/capture-preferences records how you like to work, your code taste, architecture and git habits; every session and seat follows them, the personal doc in the main session.

Navigation

Symbols, not whole files

The language servers and a scoped search locate code; a whole-file read of a large source file is blocked and pointed at symbol search.

More

Workspaces

Several projects, one install

A folder of projects shares one install's skills, rules, hooks and seats. Each project below the root joins at its own init and keeps only its own values.

Fresh session

A long session is asked to restart

When a fresh session would cost less than going on, the ask says so with the numbers, and a resume block carries the work over.

History

A record of each session

A machine-local record of each session under the data root, kept out of git.

Cursor

The same guards in Cursor

Cursor reads the stack's guards from .claude/settings.local.json; a sibling repo carries the Cursor skills and agents.

Agents

45 seats, stored per project and linked into .claude/agents as the picks are made, dispatched by their bare name (<seat>). The team matrix shows who does what, the domain cards what each seat owns, and the table at the end lists every seat with its model pin.

Every seat

Each seat with its area and how it is installed; a seat the project did not pick is not linked. Type to filter.

45 subagents

Skills

A skill is judgment loaded on demand: Claude sees its one-line description on every turn and reads the body only when the moment comes. The house skills are this stack's own - conventions per language and framework, and the workflows you start by name. The built-in ones ship with Claude Code. Type to filter; the filter is shared by every catalog tab, and each tab's count shows its matches.

88 house
14 built-in
Sources: built-in ships with Claude Code CLI · house published to envoydev/alfred-code, every skill pick copied into the project as a library copy - once, into .alfred/stack/skills, and linked into .claude/skills where git ignores that folder - and every subagent carried by the core alfred-code plugin, each one the project did not pick denied (node scripts/install/alfred-code.js install --skills-only, or the alfred-code plugin) · plugins installed via /plugin install <name>@<marketplace> · repository (plugin-bundled commands) installs with its plugin, no separate step.

Hooks

A hook is a script Claude Code runs at an event - before a tool call, after one, at a session's start, at a turn's end. A deterministic check lives here rather than in prose, because the model may skip prose and nobody skips a gate. All of them ship inside the core plugin; the How it works tab shows which event each one answers.

19 hooks

Rules

A rule is standing guidance the rule loader sends as context. The six always-on rules (alfred-*) arrive at every session start; a path rule arrives the first time a file matching its globs is touched, and its one job is to point at the skill that holds the convention.

18 rules

Commands

The core plugin's nine commands. The first time: init, restart, init again; after that, update when a release lands. Not sure which one? Type /alfred-code and it names the command to run.

/alfred-code:updateMove to the newest release fast: no selection questions, unless the release adds an item this install would not otherwise carry.
/alfred-code:configureAdd or remove skills, agents, rules, hooks and plugins: what is installed, what an update would bring, then the areas you pick.
