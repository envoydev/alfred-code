# Install footprint

Everything an Alfred Code run writes, starts and costs. The [README](../README.md) has the short version; this page is the full list, so you can check it before you install.

## In your project

Written at every scope:

- **`.claude/skills/` and `.claude/rules/`** - a link to each skill the project picked (a copy where git cannot commit a link), and one marked file for each rule it picked. A rule file starts, after its frontmatter, with the line `<!-- generated by alfred-code ... -->`; a file without that line is yours and is never touched. Claude Code loads these files itself.
- **`.claude/hooks/`** - only the five engines (`docs.js`, `history.js`, `layout.js`, `handoff.js`, `plan-status.js`) and the model-window table. The nineteen wired hooks come from the core `alfred-code` plugin.
- **`.claude/agents/`** - a link for each picked seat to its folder in `.alfred/stack/agents` (a folder copy where git cannot commit a link, and on the copy route - `/alfred-code:configure` asks which, or `--seats-route copy`). The core plugin carries no seat. A seat file of your own is kept and named. An edited folder copy in `.claude/agents` on the link route is kept and named too; an edited store copy, or an edited copy on the copy route, is overwritten on the next update with a line saying so.
- **`.claude/settings.local.json`** - the stack's settings, at every scope (3.11.0). Where git ignores the file (the stack warns when it does not), none of it reaches a teammate: their own first `/alfred-code:update` writes it on their machine.
  - `permissions.deny` - the secret-file rows. No `Agent(alfred-code:<seat>)` row is written; an update removes the ones an older install wrote.
  - the `env` block - the stack's own keys, and `ALFRED_CODE_SKILLS_VIA_PLUGIN` (`false` for the copy route, `true` for the plugin) once the agents route was switched; a switch never removes it.
  - the `attribution` keys - commit, PR and session-link attribution off, each only where the project set none.
  - custom memory's `autoMemoryEnabled: false` when the `ALFRED_CODE_MEMORY=custom` choice is made.
- **`.claude/settings.json`** - nothing the stack writes itself. At project scope `claude plugin install` enables the plugins here. An older install's rows move to `settings.local.json` on the first update; a row you changed since it was written stays here, named in the update's report.
- **`.claude/alfred-code.stamp`** - the source revision, your picks and a ledger of every write.
- **`.alfred/`** (the data root, always this folder) - the picked skills, agents and rules (`stack/`), the docs, the hooks' state (`state/`) and ledgers (`statistics/`), the seats' handoff notes and the secrets file (`.secrets`, `.sensitive-data` before). Its own `.gitignore` keeps everything but the docs out of git.

Written later, or only on one route:

- **`/alfred-code:init`** dates the stamp's `initialised:` line at its close. It never touches `autoMemoryEnabled` unless the project picks custom memory, and otherwise Claude Code's own memory stays as you set it. Custom memory writes `autoMemoryEnabled: false`, ledgered, beside the choice - into `settings.local.json` when that file holds `ALFRED_CODE_MEMORY`, so a personal choice never switches a teammate's memory off, else into the file the run writes. A personal choice never takes the team's switch-off out of `settings.json` while that file still says custom. An update or uninstall over an earlier release takes back the `autoMemoryEnabled: false` that release's init wrote.
- **`<repo>/.mcp.json`** is never written. An update over an earlier release takes the stack's own registrations out of it; a server of yours stays.
- **`.alfred/state/sessions/status/<session id>.json`** - written by the hooks, not the install, one small file per session for the session-inspector mod (now alfred-mods) to read (the context the stack acts at, the model and its window, auto-run, the scoring, a resume prompt and `plan` - the plan folder the session works on, relative to the project root, or `null`), at the project root only - the folder the session started in, or the linked worktree it started in - never a subfolder. It is written only while `alfred-mods@*` or `session-inspector@*` is enabled in the merged `enabledPlugins` (your user, project, local and managed settings); nothing overrides it, so a `--plugin-dir` session lists `alfred-mods@<any>: true` in the account `settings.json` or the project's `.claude/settings.json` or `settings.local.json` - a `--settings` file is not read. It is written at session start, at a turn's end when a field changed and when auto-run or the scoring changes; files past 7 days go at the next session start. The data root's own `.gitignore` keeps the folder out of git, so no line is written to `.git/info/exclude` for it.
- **`.claude/session-inspector/status/`** (through 3.12.1) - nothing writes there any more. The files earlier versions left there, in the root and in subfolders, go at the next session start (a subfolder's at any age; a linked worktree's, and the root's, only once 25 hours old), and so do the `.git/info/exclude` lines the old versions added for them, under `# alfred-code: session-inspector status files`.
- `/alfred-code:uninstall` takes the files back: the status files under the data root and the folder they leave empty, and the legacy files, folders and exclude lines under that comment. The mod's own files beside the old `status/` and your own exclude lines stay. The uninstall has no time limit of its own: it always takes every pair it holds.
- **`.claude/settings.local.json`** gets claude-hud's `statusLine` from `/alfred-code:init` when claude-hud is installed for this project alone - the command names this machine's `node`, so it stays out of the shared file - after a `settings.local.json.bak.<time>` copy of the file, when it already exists.

## In your account

- **`~/.claude/settings.json`** - nothing the stack needs: it seeds no account key. `autoMemoryEnabled` never lands here, whatever the install scope - custom memory writes it into the project's own settings file. The CLI's own `claude plugin marketplace add` records each marketplace the run registers under `extraKnownMarketplaces` there (code.claude.com/docs/en/plugins/loading).
- **The plugin cache** - `claude plugin install`, at EVERY scope, writes `~/.claude/plugins/cache/...` and `installed_plugins.json`.
- **claude-hud**, when you keep it - its marketplace, registered for the whole account; its install is a user-scope one only when you choose global for it (this project by default).
- **User-scope installs** - every stack plugin row, at `--scope user`.
- **`~/.claude.json`** - never written by the stack. An update over an earlier release removes the local- and user-scope registrations that release recorded, through the CLI.
- **`/alfred-code:init`** additionally writes:
  - claude-hud's `statusLine`, for a claude-hud installed globally (one installed for this project alone gets it in the project, above);
  - claude-hud's own `plugins/claude-hud/config.json` (add-only keys);
  - a `settings.json.bak.<time>` backup, taken before that run's first account write.
- **No memory database.** The stack ships no MCP server since 2.10.1; a database an earlier release left (`~/.alfred-memory/`, `~/.memory-mcp`) stays where it is, and the update that took the server out names it.

Nothing is written outside the project and the account-dir writes named above, and nothing is deleted that the run did not install.

## What runs

At install:

- One `claude plugin install` call per plugin: the optional third-party picks the project kept - `claude-hud` among them, marked recommended in every walk - and the core `alfred-code`.
- No `claude mcp add` registration at all - the stack ships no MCP server.

At every session start: the enabled plugins load, an LSP plugin starts its language server, and the hooks run. No package is downloaded or launched by the stack.

Nothing else executes from the package itself. The package itself is nine command bodies, one skill (the `/alfred-code` router; none ships a script), zero agents, nineteen references and twenty-two hooks - the core's own three (`guard-layer-table.js`, the table-before-question gate on the walk's asks and on its next `node` call, `library-stamp.js`, the startup line saying the library copies are older than the stack, and `run-dir-gate.js`, which approves the resolve block and the walk's run-dir forms and denies another session's run dir) and the nineteen stack hooks, ten of them run in-process by one dispatcher (`shell-guards.js`) on the shell tools, nine by another (`file-guards.js`) on the file tools and the turn build check (`check-turn-build.js`) inside `history-session.js`'s Stop - with no MCP server, no `bin/` and no dependencies of its own.

## What you install by hand

- `csharp-ls` and `typescript-language-server`, for the two LSP plugins - each plugin names its server and ships none. `/alfred-code:init` offers both, through its one machine-install ask: `dotnet tool install --global csharp-ls` (the .NET 10 SDK first) and `npm install -g typescript-language-server typescript@6` - TypeScript 6, since TypeScript 7 ships no `tsserver.js`, the file the server reads; it needs Node 22.22.2 or later.

## Cost per message

The whole per-message floor - Claude Code's own prompt and tools, every plugin's share (and any MCP server you registered), and the stack's pathless rules plus every agent and skill description - was measured at 87k-134k tokens across nine installs. The stack's own always-on text was 12.6k-13.8k of it. `/alfred-code:status` reports your own install's number.

## Under managed settings

- **`strictKnownMarketplaces`** - the allowlist registers nothing, and Claude Code refuses to register a managed marketplace whose source it does not admit (code.claude.com/docs/en/plugins/org). Allow each source the stack installs from - `{ "source": "github", "repo": "envoydev/plugins-marketplaces" }` (the `envoydev` marketplace, which lists the plugin from envoydev/alfred-code), `{ "source": "github", "repo": "anthropics/claude-plugins-official" }` for the `*-lsp` pair, and `{ "source": "github", "repo": "jarrodwatts/claude-hud" }` if you keep claude-hud (optional, recommended) - and register the same marketplaces in `extraKnownMarketplaces`: `envoydev`, `claude-plugins-official` and `claude-hud`, each with its matching `source`.
- **`enabledPlugins`** - one key for each plugin the project keeps; `alfred-code@envoydev` always, `claude-hud@claude-hud` when you keep it.
- **`allowManagedHooksOnly`** - silently disables all nineteen house hooks. The plugin still installs and enables, but no guard ever fires, and nothing reports it. Decide this one before rolling the stack out under a managed policy.

`ALFRED_CODE_HOOKS_OFF` is the supported way to switch individual hooks off.
