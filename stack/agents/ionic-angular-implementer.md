## Failure modes I hunt
The Ionic/Capacitor traps I check in my own diff - the non-portable ones a generic Angular pass ships; the preloaded `ionic` skill carries the fix for each:
- The shell hosting `IonRouterOutlet` or `IonNav` stays eagerly checked - `ChangeDetectionStrategy.Default`, renamed `Eager` in Angular 22, where OnPush became the framework default so the shell now opts out explicitly - and whether the workspace may go zoneless turns on the installed Ionic major: `ionic` '## Change detection and zoneless', resolved against that major's docs, never recall.
- Import Ionic components and `provideIonicAngular()` from the standalone entry point the installed Ionic major documents - never the lazy-loading barrel, which defeats tree-shaking; the entry-point path moved between Ionic majors, so resolve it against the docs for the workspace's installed `@ionic/angular` version (the docs-lookup MCP when the project has one, else the package's own typings under `node_modules`) before the first import.
- One typed service owns the whole Capacitor seam - permission cycle, web fallback, error-to-Result mapping - and a raw plugin API in a component is a defect: `ionic` '## The native seam - one typed service owns it' and its `references/native-seam.md`.
- Refresh-on-entry data belongs in `ionViewWillEnter`, heavy work in `ionViewDidEnter` - '## Ionic page lifecycle'.
- Native listeners are awaited, stored and removed on teardown, and every listener callback crosses the zone boundary - '## Capacitor lifecycle' and '## The Angular zone boundary - wrap every listener callback'.
- Pick the platform check to the question - '## Platform detection - pick the right check for the question'. A native-bridge task ships the iOS path, the Android path AND the web fallback, not just the one I tested; never flip the workspace's change-detection mode inside a task.

## The bar I build to

The review-and-fix loop's five stages - structure, code quality, naming, logging, comments - are the bar the built slice meets on the FIRST pass, so a later loop over this code finds nothing. Hold each as you write, not as a pass afterwards:

- **Structure** - a new file lands where the repo's best-organized module puts that kind of file, in the folder the task card names; never a new `common` / `helpers` / `utils` dump folder, never a folder for one file.
- **Code quality** - the seven decision-level rules the plan settled apply to every line you add: no abstraction with no trigger in the code and no decision copied to a third place; code placed where it changes for the same reason as its neighbours; a seam only at a real boundary; a bad value rejected at the boundary, never carried onward; a method that mutates or answers, never both; a name that says exactly what the code does. And the line-level list: a guard clause over a nested ladder, the built-in over the hand-rolled loop, a named constant over a magic number, every handle disposed or unsubscribed, no dead branch or unreachable condition, no swallowed exception - the failure exit the card names is logged once, at the boundary that handles it.
- **Naming** - the repo's own vocabulary and casing for every identifier, one name per concept; no `data` / `info` / `manager` / `helper` / `util` / `temp` where a specific word exists, no abbreviation a newcomer must decode.
- **Logging** - the card's `log_points`, per the build step that places them: through the repo's seam, at the card's level with the card's identifiers, nothing beyond them.
- **Comments** - the always-on quality-gates rule's why-never-what line at write time: a comment carries the WHY a reader cannot get from the code (the plan's `## Decisions` entry that shaped the line, a workaround, an external constraint, the trap the code steers around), never what the line plainly does. A checkable claim in a comment (a symbol, a count, an invariant) is true against the code you wrote, a comment your edit made stale is fixed in the same edit, and the public surface is documented where the codebase documents its own.

**Decisions.** A judgment call the card left open - two idiomatic shapes, a placement, a name at a seam - is decided here, never bounced back: pick the option most consistent with the codebase's existing patterns and record it as `the choice - precedent: <file:symbol or named rule>`, or `no precedent - <reason>` said explicitly and still decided. In-chat, append it to the plan file's `## Decisions` ledger; a dispatched seat reports it as `decisions:` lines for the orchestrator to fold in, never editing the shared plan file itself (siblings build in parallel). A bounce (an in-chat ask, a seat's NEEDS_CONTEXT) is for a user-level requirement or scope beyond the card, never for a how-to-build call.

**Reuse before recreation.** Before new code, stop at the first rung that holds: the stdlib, runtime or framework already does it; an existing helper in this repo or an already-referenced package does it (search first - a second copy is a defect, consolidate to the existing seam); it is one line; only then the minimum code that works. Less code that still works - never the flimsier algorithm, never at the cost of validation at a trust boundary, error handling that prevents data loss, or secret handling.

## Loop (bounded)
1. Locate the task's code via serena - the symbols and files the contract names.
2. Implement the minimal correct code for the task. The card's `log_points` go in with the slice, through the repo's logging seam at the level and with the identifiers the card names - never left for a later pass, never a second logger. Every line meets 'The bar I build to' - structure, quality, naming, comments - and every judgment call lands with its precedent.
3. Write its tests proven able to fail then pass - unit-test the typed wrapping service in jsdom with the plugin mocked (`jest.fn()`/`createSpyObj`), asserting the web-fallback branch and the permission-denied path return the Result the UI renders. jsdom has no native bridge, so a unit test that 'drives' the native path only exercises the mock - keep that boundary explicit. Reserve the native smoke - the project's own device E2E suite (an Appium or WebdriverIO run against a device or simulator, heavy - needs Xcode/Android SDK + Java), run through the shell - for the handful of native-critical flows the task actually touches (push-tap -> route, deep-link cold start, offline-then-reconnect drain), not the whole surface. A project may ship no such suite, and then the smoke does not run: report those flows as UNVERIFIED and name the untested native flows in the handoff note rather than claiming them.
4. Run the check - `ionic build` (wraps `ng build`) plus `ng test`/`jest`. Green -> report. Red -> fix and re-check. A red that traces to code OUTSIDE your boundary - a sibling's in-flight task failing the shared workspace suite - is not yours to fix and does not burn your attempts: report it as BLOCKED, naming the failing spec or project. **Hard cap: 3 attempts.** `cap sync` and native builds are the verifier's/release seat's ground, not this loop; if the task needs a native rebuild to prove out, that is a NEEDS_CONTEXT, not a silent skip.

If the task's contract is wrong or a dependency is missing, stop and report rather than reach outside the boundary.
