# The security method

The six steps `review-security` runs, in order, over the target only. Locate a symbol through the navigation tools (the symbol with its body, its callers, a file's outline) before you read code; Read is for code already located.

1. **Repo context.** Before judging the change, learn what the project already uses: its validators, sanitisers, encoders, authentication and authorization helpers, crypto wrappers, secret store and query builders. Name each one found with its `file:line`. A finding later cites the helper the change should have used.
2. **Departures.** A change that does the job one of those helpers does, without it: a hand-built query beside the project's parameterised builder, a hand-rolled token check beside the auth middleware, a new endpoint missing the policy every sibling carries. A departure is a candidate even before a taint trace proves it.
3. **Taint trace.** Each NEW input the change adds or widens - a request field, a header, a route value, a file, a message, a deep link, a value read from the database or a tool result - followed to the sensitive call it reaches: a query, a command, a file path, a template or HTML sink, a redirect, a deserialiser, a crypto call, an authorization decision. Write the hops down; a trace that breaks at a validator from step 1 ends there.
4. **Categories.** Sweep the target against the security-auditor seat's category list (secrets, authentication, authorization, input and injection, configuration, data exposure, dependencies, mobile, extension, desktop and service) and the touched stack's own security skill where one is installed, locating the code for every candidate. When no installed skill matches, keep the finding in this report tagged with its surface and mark it UNVERIFIED.
5. **Confidence.** Score each candidate 1-10 on how sure the located code makes the exploit: 8-10 is a finding (a traced path, a known pattern with the guard absent), 5-7 a lead (real if one condition the code does not settle holds), under 5 dropped as noise. A lead names what would prove or clear it. A finding's severity is HIGH (directly exploitable: code execution, data breach, auth bypass) or MEDIUM (needs one further condition, significant impact); a LOW finding is a lead.
6. **Refute pass.** Each finding and lead is checked against `not-a-finding.md`, and each finding gets one more read of the line it cites: a guard upstream, a framework default, a caller that never passes the input. A quoted line or a precedent that clears it refutes it; a refuted one is dropped, never moved to the leads. Merge near-duplicates first (one root cause, one row).
