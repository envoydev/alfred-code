# The COMMIT-GATE receipt - when this review is the pre-commit checkpoint

Read when a commit is the next act and the verdict is sound - or sound after fixes that landed and
re-verified. A punch-list with unresolved BLOCKER/MATERIAL findings writes no receipt.

Write the gate receipt `<docs-path>/flow/COMMIT-GATE` with five lines - `VERIFIED <what was reviewed, one phrase>`, `authorized: "<the user's words asking for THIS commit, verbatim>"` (or `answered: <the chosen option label>` when they picked rather than typed), `head: <the sha reviewed>`, `spec: <N files>` and `live-probe: <what you ran, or NOT RUN - <reason>>`. On a security-relevant diff (auth, crypto, secrets, payment, data access) the receipt adds a sixth line: `security:` naming each category checked and its verdict (`security: auth ok, secrets ok, injection ok, data-access n/a`), written only after the `/security-review` pass alfred-security requires - a VERIFIED line that claims that review with no `security:` line reads as no review. The VERIFIED line proves the review ran, the authorized line proves the user asked. When the consent words do not exist yet - the review ran ahead of the ask - write the VERIFIED line now and append the authorized line at the commit turn, before the commit call; write the receipt as its OWN tool call, never inside the commit's compound command. The `guard-ungated-commit` hook blocks a non-trivial commit without all of them, and an INLINE review's Output may live in the receipt provided every required field is present.
