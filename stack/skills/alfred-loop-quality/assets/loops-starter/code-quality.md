# Code quality stage

A findings-based audit. Review TARGET for correctness, clarity, and conformance to the project's recorded architecture. Run it after the structure stage - once files have stopped moving - and before naming: it carries the widest blast radius of the remaining stages now that it covers structural conformance. Whether a failure path is VISIBLE - its log point, level and identifiers - is the later logging stage's; here you decide whether the catch, the fallback or the exception is right at all. Architecture-level restructuring (introducing a new boundary, inverting a layer wholesale, adopting a new pattern) is out of scope here - that is the `alfred-loop-architecture-quality` skill; in this stage you flag where the code violates the structure already recorded and fix it with the smallest correct change.

First, read `<docs-path>/architecture/ARCHITECTURE.md` if it exists - the recorded layers, boundaries, dependency directions, and patterns - then audit TARGET against it and against general quality.

Look for:
- **Architecture conformance** (against ARCHITECTURE.md): logic in the wrong layer, a controller doing persistence, a domain model reaching into the UI; a dependency pointing the wrong way (a core depending on a detail) or a cycle between modules; a second architecture pattern bolted onto the one the map records - match the recorded structure, never introduce a rival even if it is better.
- Bugs: off-by-one errors, null and boundary mishandling, swallowed exceptions, the wrong operator, an unhandled async rejection. Report a bug only with a constructible trigger - the concrete input, state, or sequence that makes it misbehave; a smell you cannot trigger is not a bug finding.
- Dead code, unreachable branches, and conditions that can never be true or never false.
- Needless complexity - a nested conditional ladder that flattens to a guard clause, a hand-rolled loop that is one built-in call, a re-implementation of something the standard library already does.
- Resource and lifetime issues: leaks, unclosed handles, mutation of shared state, a missing dispose or unsubscribe.
- God objects, files, or functions that have accreted unrelated concerns; magic numbers and copy-pasted blocks that should be a named constant or a single function (rule 1 below sets WHEN to extract).
- **The working set - seven decision-level rules the audit judges against.** Three questions on every change: is this the right TIME for the abstraction (1), the right PLACE for the code (2-3), and can it lie to a reader or hold a bad state (4-6)?
  1. **YAGNI + rule of three.** Write the direct solution, copy it once, abstract at the third occurrence - splitting on what actually varied. Both failures are findings: an abstraction built with no trigger (a strategy interface with one implementation forever, an extension point nobody extends), and the same decision duplicated across three sites. A shared helper growing boolean parameters to serve diverging callers is an early seam - split it back. This is where the loop gets open/closed on demand: the third variant shows the seam instead of you guessing it, and it subsumes DRY with better timing - duplication is a finding only when the copies encode the same decision and change together.
  2. **High cohesion, low coupling - the placement test.** Does this code change for the same reason as its neighbours? A class or file with two axes of change fails it, and so does the opposite miss: forty anemic classes where four belonged. Run it on the diff, not on a taxonomy.
  3. **Program to an interface at boundaries ONLY.** A seam where one really exists - an external system, something you mock, something with two implementations or a credible second. An interface-per-class mirror with a single implementation is ceremony and a finding; a fat interface whose consumers call a fraction of it is the same failure from the other side.
  4. **Illegal states unrepresentable where cheap, fail fast everywhere else.** Constructor validation, required fields, closed hierarchies for domain state, enums over strings; where the type system will not help, validate at the boundary and throw - a known-bad value travelling onward is a finding. Default to composition and inherit only for true substitutability; a `NotSupportedException` in an override, a strengthened precondition, or a narrowed return is the Liskov tell.
  5. **Command-query separation.** A method either mutates or answers, never both.
  6. **Least astonishment.** The name is the contract - a method doing more than its name says means fixing one of the two. Fix the behaviour here; when the honest fix is the name, leave it to the naming stage.
  7. The boy scout rule needs no bullet - this pipeline IS it, bounded by the fix discipline the `0.`-numbered file holds.
  SOLID stays review VOCABULARY ('this violates Liskov' is a precise, fast comment), never the audit's basis: a candidate whose only support is a letter of the acronym, with no breakage named, is not a finding.
- **A hand-rolled shape where a documented pattern fits, and pattern-first indirection - the same error in both directions.** Once rule (1)'s trigger is in the code, use the established pattern rather than a bespoke structure and name it - GoF at object level; layered, hexagonal, event-driven, pipes-and-filters or MVC at system level; outbox, saga, circuit breaker or idempotent consumer at the integration level - for the vocabulary, the tradeoffs someone already paid for, and the reader who predicts the rest from a fragment. Absent a trigger the simpler structure wins: refactor TOWARD a pattern, never start from one. A pattern the language has absorbed (first-class functions, closures, generics, pattern matching) is a keyword now, not a structure to build; match the forces a pattern resolves - variation vs stability, coupling vs cohesion, flexibility vs directness - not its class diagram.
- **Named anti-patterns**, findings in themselves and easier to point at than the virtues: big ball of mud, anemic domain model, distributed monolith, premature generalisation (the god object and the copy-paste block are above).

Where a file LIVES - its folder, the tree around it - is the earlier structure stage's; naming and comment findings are owned by the later stages. Do not flag any of them here, even when you spot them. A choice recorded in AGENTS.md or the architecture docs is a decision, not a finding - judge the code against what the project deliberately chose, never against a convention it deliberately does not use.

Severity: a real bug, a dependency cycle, or a cross-layer leak is a BLOCKER; a Liskov violation, a shared helper coupling callers that change for different reasons, or an abstraction built with no trigger is MAJOR (delete the abstraction; do not grow it); an awkward-but-correct expression or a single misplaced helper is MINOR. Make the smallest change that resolves each finding - move code to its correct home, extract the constant - without rewriting a working module wholesale; a fix that introduces new findings is divergence, not progress.

A deviation from a preference is not a finding unless you can name what it breaks - a wrong finding costs more than a missed one.

Bar: zero findings at every severity - real findings only: a candidate with nothing nameable it breaks is not a finding (not recorded, not counted against this bar), `open: []` on pass 1 is a valid, complete result, and every real finding is listed, never trimmed.
