# Domain Trio Protocol - One Stack's Design, Build, Verify Vertical

The execution protocol for the single-stack modes (`domain_trio`, `fanout_domain_trio`). By the time this file is read, the scoping verdict has already named the stack - a user hint ('frontend only', 'just the API') pins it the same way. The seats are resolved from the installed roster by the naming pattern `<stack>-solution-designer` / `<stack>-implementer` / `<stack>-verifier` (the generated capabilities rule lists what this project actually has). A seat may register under a NAMESPACE (`<namespace>:<seat>`) rather than as a bare name, and where it does only that spelling resolves - dispatch each seat exactly as the roster spells it, never as the bare pattern below. Everything technology-specific - conventions, patterns, what a good design or a passing verify looks like - lives in the seats and the skills they load, never here.

DELEGATED vs INLINE is picked once, before DESIGN - the calling skill's run-start session-or-agents ask decides it (deep dive: `task-solve-cross`'s `references/execution-modes.md`, where installed): DELEGATED dispatches every seat; INLINE does the same three steps in-session - design, build the tasks in the designer's order, verify against the plan - each through its single-chat twin where installed (`task-design`, `task-implement`, `task-verify-code`; a twin inherits the recorded mode and never re-asks), so an inline plan carries the same card contract a dispatched designer's does - traps, anchors, `log_points`.

## Steps

1. **DESIGN** - dispatch the stack's solution designer with the clarified requirement (the clarify gate already ran in the skill body - never design against a guessed one). The seat has no Write tool: it returns the plan in its report, `Oriented:` line first, and you write `<docs-path>/plans/<feature>.md` from it before the gate below. Check the returned decomposition for BALANCE and file boundaries before dispatching seats: a task card whose surface (entities/files touched) is a large multiple of its siblings gets re-split (measured: 2 of 7 one-task seats carried 67% of a run's implementer spend at 13-18x their siblings), and two cards sharing a build-colliding file run serial, never parallel (measured: a concurrent pair tripped a transient compile collision on a shared file), and a card missing one of its stamps - `implementer_model`, `anchors`, the acceptance criterion, `log_points` - is a scoped re-brief to the designer, never a fan-out. For a diagnosed bug the plan comes from the diagnosis instead (`task-solve-cross`'s `references/issue-investigation.md`, where installed). Either way the output shape is the same: the architecture or the proven root cause, the test strategy, and a decomposition of independent tasks with contracts (each task's boundary and what it hands off or depends on). Gate the returned plan before anything builds - invoke `task-verify-plan` (the Skill tool, never its passes replayed from memory) and run its five passes in-session, recording the five per-pass verdicts (`risk / scope / existence / edges / soundness`) in the ledger; a failed pass is a scoped re-brief to the designer - then STOP: present the gated plan and put the review to the user via AskUserQuestion - approve-and-build vs changes-needed, free text via Other (plain-text options where the harness lacks the tool) - and build only on the approving answer, which is the explicit word the calling skill's plan review stop and any approval gate file quote verbatim. A blanket dispatch opt-in in the ask is NOT that word, and neither is a run-the-whole-flow or completion-token instruction - only an explicit review waiver ('run without plan review') skips the stop, recorded as `plan_review: waived` in the ledger. Never fan out against an unaudited, unreviewed, or unapproved plan. The receipt is the gate: BUILD does not start - dispatched OR inline - until the ledger carries `plan_review: approved - "<their words>"` (or the waived form); in DELEGATED mode write the approval gate file from those same words before the first implementer dispatch (the dispatch hook enforces the file; the ledger field is the gate INLINE mode has). A build step reached with that field absent is a protocol violation, headless runs included (measured: two headless runs built straight past this stop; the one dispatch attempted without the stamp was stopped only by the hook).
2. **BUILD (fan-out)** - dispatch one implementer per independent task in parallel from the main session, up to 3 at once (more only on the user's ask), queueing the rest as seats return. Fan out every task the designer marked independent, not a token two. Hand each implementer exactly one task plus its contract; it never touches anything outside its boundary, which is what keeps the parallel runs collision-free. Two independent tasks whose file lists share a DIRECTORY dispatch with `isolation: "worktree"` on the Agent call - each seat in its own git worktree - but only from a clean tree (`git status --porcelain` shows nothing outside the docs root): a worktree carries commits, never the uncommitted edits a dirty tree holds, so there such a pair runs serial. The worktree branches from this HEAD because the install seeds `worktree.baseRef: "head"`; under the default `"fresh"` it branches from the remote default branch and misses every unpushed commit. Such a brief pins the base sha (`git rev-parse HEAD` at dispatch), follows the worktree step zero below, and tells the seat to leave its edits uncommitted there. Tasks in disjoint directories keep the shared tree. Write context shared by several tasks ONCE - in the plan file or the navigation-server handoff note - and point each brief at it instead of restating it per brief: brief authoring stays in the orchestrator's context permanently, and a measured 12-brief fan-out restating the same context carried ~64k of it. Shared context includes the CONSTANTS and surfaces several tasks program against - a config threshold, a shared fixture's exported symbols - so a dozen seats do not each re-read the same file for one value (measured: one config read 14x and one fixture ~90 ranged reads across seats). And the pointer each brief carries is a per-task SLICE - the task's own section as a line range, or its card in the handoff note - never the whole plan file's path: seats pointed at the plan each read all of it (measured: 7 whole-plan reads across 5 seats, ~71k tokens, for tasks that each needed one section). Dispatch each with the `implementer_model` the designer stamped on the task card, passed as the per-dispatch model override; the seat's frontmatter pin is the fallback when a card carries none (full rule: `task-solve-cross`'s `references/model-routing.md`, where installed - the card's stamp and the frontmatter fallback are the operative parts).
3. **VERIFY (fan-in)** - once every task lands, dispatch the stack's verifier over the assembled whole, never over a single task. A seat that ran in a worktree lands only when its change is back in the main tree: its completion names `worktreePath` and `worktreeBranch` when the worktree held changes (an unchanged one is already removed). From the main checkout, `git -C "<worktreePath>" add -A && git -C "<worktreePath>" diff --cached --name-only <base sha>` lists what it changed - a path outside the task's boundary is a breach, routed BLOCKED, never applied - then `git -C "<worktreePath>" diff --cached --binary <base sha> | git apply && git worktree remove --force "<worktreePath>" && git branch -d "<worktreeBranch>"` lands it uncommitted, all or nothing; a failed apply changed nothing and keeps the worktree, routed BLOCKED to the owning implementer. Never commit a seat's work to fan it in: the commit gate judges the main checkout's diff, not the worktree's, so a seat's commit passes or blocks by what its siblings left there. This fan-in is a checked step: the round-close report names the verifier dispatch - or, in INLINE mode, the explicit self-verification it substituted - and a round that landed implementer work cannot close without one (measured: a 14h run landed ~30 substantial implementer tasks with zero verifier dispatches, leaving the same context that authored the plans to also gate them; the one regression avoided that run was caught by the designer step, not verification). On a punch-list, route each item back to the implementer that owns it, **resumed with a scoped brief** - the failing assertion or check plus the file and symbol to touch, not a fresh full-context re-brief (a full re-dispatch roughly doubles the cell's cost for a one-line fix) - then re-dispatch the verifier. The verifier's independent checks (build, the test suite, the contract-seam probe) are parallelizable - run them concurrently where the seat supports it. Loop until sign-off, but bound the loop: **two implementer fix rounds maximum**; still failing after that, stop and put it through ONE AskUserQuestion - 'Re-plan the task with the designer (Recommended)' / 'One more scoped fix round' / 'Stop and report BLOCKED' - rather than looping to sign-off forever.

## Bookkeeping

- **Progress ledger.** The run's ledger is the same durable file `task-solve-cross`'s `references/agent-output-protocol.md` formats (where installed - a plain per-task status/verdict table serves without it) - every task and its status, each verify pass, and the contract_version when the run sits under a frozen cross-domain contract - so a mid-run compaction resumes without re-deriving what already landed.
- **File hand-off, per-task review.** Each implementer gets its task + contract as a written brief and returns a written report; glance at each task's diff the moment it returns - not after the whole fan-out, and not by serializing the implementers. The verifier still runs once over the assembled whole; the early glance only catches a contract breach before it compounds.
- **Status routing.** Route on each implementer's closing status: DONE -> hand to the verifier; DONE_WITH_CONCERNS -> carry the flag to the verifier; NEEDS_CONTEXT -> close the gap via the designer, then re-dispatch; BLOCKED -> sequence after the blocking task; BLOCKED_CONTRACT_CHANGE -> pause the affected work and run the contract-change protocol (`task-solve-cross`'s `references/contract-protocol.md`; absent it, pause the lane and put the change to the user). The routing lives here; the status definitions and structured shapes are that same skill's `references/agent-output-protocol.md`. A return with no closing status line - a seat stopped at its `maxTurns` (Claude Code marks the output partial from 2.1.246) or killed mid-task - is never DONE and never resumed as-is, since a resume hands a runaway a fresh budget: route it as a seat death (below) - ONE scoped re-dispatch; a second status-less return from that task goes to the user as BLOCKED.
- **Seat death.** A seat killed mid-task by API errors (5xx / overloaded) is re-dispatched with a scoped resume brief - its handoff note and partial diff name what already landed, the brief carries only the remainder - never finished inline by the orchestrator (measured: four implementers died in one outage window and their tests, finished in the main session instead, pulled build work into a ~380k-ctx context). A death re-dispatch resumes the same round - it never consumes a verify fix round; when no handoff note was written yet, the partial diff alone scopes the resume. Deaths cluster in outage windows - re-dispatch after a short pause, not instantly.
- **Memory hygiene.** The navigation-server handoff notes live in the gitignored `<data root>/serena/memories/` (`.alfred/serena/memories/` by default; a 2.0.0 `.serena/memories/` until its move) and outlive a branch switch. ONE naming grammar: `<feature>/<contract_version>/<seat>` for a single-note seat (designer, verifier, diagnoser), with a trailing `/<task>` segment for implementers (one note per task) - each `/` is a folder, so one run's notes sit in one folder the server filters by (serena 1.7.0's `list_memories` `topic` lists that folder and nothing else; a name prefix filters nothing), and `<feature>` is never `global` (serena files a `global/` name in its home's shared store) - and the ORCHESTRATOR mints `<contract_version>` and puts each seat's literal note name in its dispatch brief, verbatim; a seat never derives its own name from the pattern (measured across three projects: seats handed only the pattern produced 3-5 incompatible schemes per run - feature and version swapped, literal `contract_version` text baked into names - and one read failed on a guessed name). A seat reads only its run's notes - `list_memories` with `topic: '<feature>/<contract_version>'` - never a stale one. After the verifier signs off, purge the run's notes (the navigation server's `delete_memory` on each note under `<feature>/`, or an `rm -r` of that folder, which also takes the empty folders `delete_memory` leaves; a run begun before 2.1.6 named its notes `<feature>__*`, and they go too) so they never bleed into a later run that reuses the workspace - and the round-close report carries the receipt, `memories purged: <names|none>`, as a REQUIRED field the close is incomplete without - and a close whose deletes trail the run's writes is incomplete even with the field present (measured: one run wrote 27 notes and deleted zero, a second wrote 28 and deleted zero, and two projects accumulated 79 and 55 stale notes - a purge instruction with no report field is skipped every time). The purge is FOLD-FIRST: before deleting, anything in a note that outlives the run - a flagged-but-unfixed bug, an owed gate, a decision the close must report - is folded into the ledger/task docs or the close report; an unconditional purge once destroyed the sole record of a flagged bug (measured). An `rm` of the note files is the same purge (the memories folder is plain files) - it satisfies the receipt identically; what matters is fold-first, then delete, then the receipt names what went.
- **The purge is counted, not claimed.** At close, from the project root: `node -e "const fs=require('fs');const f=process.argv[1];let n=0;function walk(d,rel){let es=[];try{es=fs.readdirSync(d,{withFileTypes:true})}catch(e){return}for(const e of es){const r=rel?rel+'/'+e.name:e.name;if(e.isDirectory())walk(d+'/'+e.name,r);else if(e.name.endsWith('.md')){if(r.startsWith(f+'/'))n++;else if(r.startsWith(f+'__'))n++}}}walk((process.env.ALFRED_CODE_DATA_PATH||'.alfred')+'/serena/memories','');walk('.serena/memories','');console.log(n)" <feature>` with the run's own `<feature>` - it counts the notes under `<feature>/` and a run begun before 2.1.6's flat `<feature>__*` ones, in the data root's folder and a 2.0.0 one not moved yet (a missing folder means none are left), in node so no `find` first on PATH decides it (Windows' `find.exe` is a string search). Quote the number beside the receipt; above zero the close is not 'done' - fold and delete the rest, then count again.

## Rules

- The main session is the only orchestrator for the whole vertical. The domain seats carry no Agent tool - the fan-out stays flat, and no seat is ever told to dispatch another.
- **Seat gates are fast.** An implementer's green gate is the stack's build plus the relevant fast tests only - never a minutes-long verification (an integration/replay suite, an E2E pass) in any seat's dispatch brief. A dispatched seat cannot cheaply wait on one: measured, it idles on the run, spawns overlapping background monitors, and burns about half its cost on wake-up churn without ever delivering its report. The slow, full verification runs ONCE over the assembled whole, owned by the main session after fan-in - never delegated into a seat, the verifier included. Coverage measurement is not a build gate at all - it runs on its own deliberate cadence via the `capture-test-coverage` capture.
- **On-demand skills can be absent.** A seat's frontmatter preloads always install with the seat; the skills a brief tells it to load on demand are per-project - narrow specialists that arrive only where the project's stack or evidence shows the area. So a brief DESCRIBES what such a skill covers rather than naming it, and you match it from YOUR skill list by what each skill says it covers - never by a remembered name. A name only works where the skill exists; a description also tells a seat without it what to do. Nothing matching means the project has no such surface: work from the preloaded conventions (a guessed name fails 'Unknown skill' and the seat burns the turn absorbing it). The same holds for an MCP server the baseline does not lock: a brief describes what the server does, and the seat reports the checks it could not run as UNVERIFIED - never a bare server name.
- **A worktree brief carries its own step zero.** When a brief isolates an implementer in a git WORKTREE rather than the shared tree, it states the pinned base sha, and step zero is `git rev-parse HEAD` against the brief's pinned base sha: on mismatch, `git merge --ff-only <base>`, and if that cannot fast-forward the seat STOPS and reports BLOCKED rather than build on stale code. Name the stack's stale-base tell in the brief so the seat recognises it instead of debugging it - on .NET, a restore suddenly failing with NU1901-NU1904 NuGet-audit errors nobody caused (the old base pins package versions whose known CVEs newer commits already fixed - return to step zero, never suppress the audit); on TypeScript, a compile error about a symbol that exists on HEAD, or an `npm ci` lockfile or audit failure nobody caused. The brief is the only place that knows the sha, so a worktree brief without it is incomplete.
- Fan out only the tasks the designer marked independent, and respect the contracts it drew between them - two implementers touching the same boundary is the collision the contracts exist to prevent.
- The architecture docs are not refreshed by this flow. The fit verdict (extend / refactor first / isolate) is the designer's call from the committed map; reconciling the docs after a structural change is a deliberate capture run (`capture-architecture` / `loop-architecture-quality`), never a step here.
