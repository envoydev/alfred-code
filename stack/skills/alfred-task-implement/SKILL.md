# Project Implementer - execute a verified plan, task by task, in one chat

The build step of the single-session vertical: `alfred-task-design` planned it, `alfred-task-verify-plan` audited it, this executes it one task at a time in dependency order, every diff inspectable as it lands. Conventions need no restating - the path-scoped rules attach the house and project style per file type, and the task cards name the stack traps. The plan FILE is the whole input: run this in a fresh session (or `/clear` between tasks) and context stays at plan size. `references/protocol-in-full.md` carries every rule below unabridged with its reason; `references/evidence.md` the measurements.

## Build mode - this chat or the implementer seats

1. **Pick the mode.** When the invocation names no mode and no calling flow recorded one (`alfred-task-solve`'s `mode <session|agents>` line, an orchestrator's brief), ask ONE question before building - this chat, or the implementer seats? - and hold it; a mode already picked is inherited.
2. **In-chat** builds by the protocol below and dispatches nothing. **Agents**: each task to its `<stack>-implementer` seat, up to 3 at once - read `references/protocol-in-full.md`'s Build mode first: the APPROVAL stamp, a refused stamp, and each seat's gate stays build + fast tests, never a minutes-long run like integration replays or an E2E pass; the full suite stays with this session's finish step.
3. **No `Approved:` line** in a plan this skill was invoked on alone: ONE approval ask before task 1, written back as `Approved: <date> - "<the user's words, verbatim>"`.

## The protocol - per task, in plan order

Before reading the plan, load `alfred-habits-plan-writing` (the card and status shape) and `alfred-habits-test-first`, the loop every card's `test:` runs on.

1. **Take exactly one task.** Its card is the contract - owned files, named traps, `file:symbol` anchors, the `test:`, the acceptance criterion. Mark it `IN_PROGRESS` in the plan file before code; jump to the anchors, never re-navigate.
2. **Build the slice + its tests together.** The card's `test:` comes first; its red on the criterion's assertion is the only red that counts. The card's `log_points` go in with the slice, through the repo's logging seam at the level and with the identifiers the card names. Every line meets the bar below; stay inside the task's boundary - a change outside it is a flag.
3. **Gate the task green** - build + the relevant tests after each task, every red fixed INLINE with each run quoted. After the FIFTH red run of one gate the next act is ONE AskUserQuestion - keep fixing inline / a resolver seat / stop - never a sixth run.
4. **Close it honestly** (`alfred-habits-done-gate` loaded before the first close): run the acceptance command and quote it, tick `DONE` with that evidence in the plan file, append the task's judgment calls to `## Decisions`, refresh the one-line resume note - never more than one task stale. A criterion that is a RUN not yet made stays `IN_PROGRESS` with `needs: <the run>`; a `FAILED` task ends the turn on ONE ask - continue inline / resolver seat / stop / revert.

## The bar I build to

The review loop's five stages are the bar the built slice meets on the FIRST pass - held while writing, not after; `references/build-bar.md` carries each rung, read before a plan's first task:

- **Structure** - a new file where the repo's best-organized module puts that kind of file; never a dump folder or a one-file folder.
- **Code quality** - the seven decision-level rules the plan settled apply to every line you add, the line-level list with them.
- **Naming** - the repo's own vocabulary, one name per concept; no `data` / `info` / `manager` / `helper` where a specific word exists.
- **Logging** - the card's `log_points` only, through the repo's seam.
- **Comments** - the why, never the what. A checkable claim in a comment (a symbol, a count, an invariant) is true against the code you wrote; a comment your edit made stale is fixed in the same edit.

**A model change never leaves its task without its migration** - generated by the tool, or hand-written when the tool cannot run here; a schema model with no migration fails every integration test at boot (EF: `PendingModelChangesWarning`).

**Decisions.** A judgment call the card left open - two idiomatic shapes, a placement, a name at a seam - is decided here, never bounced back: the option most consistent with the codebase, recorded as `the choice - precedent: <file:symbol or rule>` (or `no precedent - <reason>`) in `## Decisions`; a seat reports `decisions:` lines instead.

**Reuse before recreation.** Before new code, stop at the first rung that holds: the stdlib or framework does it; an existing helper or referenced package does it; it is one line; only then the minimum code that works.

**Callers first on a bug fix.** List the function's callers (`find_referencing_symbols`) and fix once where they all route through - a guard on only the reported path leaves every sibling caller broken, and one guard in the shared function is also the smaller diff.

## When the plan meets reality

- **A task proves wrong mid-build** (the seam isn't where the plan said): stop and name the delta, then ONE ask - re-design this slice with `alfred-task-design` (recommended) / continue against the delta / stop. Reality wins through a revision, never a drift.
- **A tool the environment blocks** (a generator hanging on denied egress, a command the sandbox refuses): the task still finishes here - take the in-session route before any ask. For an EF migration: `dotnet ef migrations add <Name>` with `--project` AND `--startup-project` both set to the project holding the design-time DbContext factory, which boots no host (pilot 3: the API-as-startup runs never produced one; the Data-project run took 3 s); failing that, hand-write the migration and its model-snapshot change from the nearest prior one. Only a task with no in-session route becomes a blocker ask, recommending the route - never 'retry the same command' or 'you run it'.
- **Scope beyond the plan** (a nearby bug, a refactor itch): ONE ask - add it to the plan / leave it for later; never rides along. A bug reported after `Completed:` asks fix now / new cycle / defer.
- **A shared contract surfaces** (a DTO both sides compile against): stop - that is `alfred-task-solve-cross`'s BLOCKED_CONTRACT_CHANGE.

## Finish - the in-session verifier

All tasks green: run the full suite once, then the review your choice names - `alfred-task-verify-code` inline, or the `<stack>-verifier` seat - pointed at the plan file, its findings applied; then the done-gate on the whole feature. Report one line per task - `task | status | evidence` - then the suite and review result and the `## Decisions` entry count. A deliberate simplification this build made is filed as a Known ceilings row, never a code comment - `references/known-ceilings.md` has the commands.

`references/worked-example.md` builds a three-task plan to DONE and shows the report - read it before the first task of a session's first plan.

## Don't game it

The acceptance criterion is satisfied by behavior, never by weakening the test that checks it. A green gate means the commands ran and their output says green - quoted, not assumed. Never suppress a warning, stub a path, or narrow a test to advance; a task that cannot go green honestly goes back to design as a named delta.
