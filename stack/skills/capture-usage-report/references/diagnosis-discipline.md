# Stack usage report - diagnosis discipline (the step 4 gate)

Read at the start of step 4 WRITE, before the first authored row of any bundle; the report's Environment rows carry `Discipline: read` as the receipt. Every check here is a rule a hand-written report broke - apply each to the row it names before the row is written, and when a check and your recollection of the transcript disagree, re-open the transcript.

## Environment rows
- The rows you author derive from the AUDITED transcript (its own `version` field - the analyzer prints it); any row describing the analysis run's environment is labeled as such. A cited rule or clause is checked against the skeleton's machine-written `## Session vintage` block before 'the session broke rule X' is written: it names the install the session loaded (the stamp's version and date against the session's own window) and, per skill run, whether the body the transcript actually loaded differs from the current source. A `DIFFERS` row means today's source is NOT what the session read - quote the loaded body or drop the claim; `body not captured` means no comparison is possible, which is not the same as `same`.
- A fresh-session claim reads its threshold off the window the skeleton's own **Models** row maps to in the install's `.claude/hooks/model-windows.json` (an unlisted model: `ALFRED_CODE_DEFAULT_CONTEXT_WINDOW`, 300,000 seeded), never a remembered constant or an id suffix: a 1M window is gated by `ALFRED_CODE_FRESH_SESSION_1M` (400,000 seeded), a 200k one by `ALFRED_CODE_FRESH_SESSION_200K` (150,000), and any other or unknown window by `ALFRED_CODE_FRESH_SESSION_DEFAULT` (300,000 - a trigger at or above the window clamps to 90% of it, 270,000 on the seeded default) - judged against the **Peak context** row, never the average. Those are the SEEDED defaults: where the audited install's own settings.json is not readable, say the claim is against the default rather than against that install's value.

## Per skill run - the rows and what each carries
- Tokens and tool-call counts cite the Tokens/Tools table rows - never restate the numbers in prose; restating is where wrong claims come from.
- **Did the run PRODUCE anything?** Each per-run row names the artifact it left behind - the file written, the registration changed, the answer delivered - with the turn that did it. A run that ends with no Write, no Edit and no answer is ABANDONED, and saying so is the row's whole job.
- Top 10 most expensive tool RESULTS by ~tokens, each as: tool | target (file path or command only, never file contents) | ~tokens - measured from the transcript (the analyzer aggregates per TOOL, not per result); label them as transcript measurements. Each row carries the `tool_use_id` it was measured from, so a cause claim points at one call and not at a neighbour.
- Context-growth spikes the analyzer flags, and what caused each.
- Skills/plugins that attributed output (the analyzer's attribution columns) - did the run load anything unexpected, or fail to load something it should have? The analyzer prints main and subagent attribution SPLIT, with the seat types carrying each sub stamp: a seat type foreign to the skill (a domain verifier under an installer command) is stamp bleed from an adjacent run - a dispatched seat inherits whatever skill was last active - so report it as bleed and never charge it to the skill.
- Subagent dispatches, mode-aware. Single-chat skill: should dispatch nothing - any subagent cost is a finding, not a footnote. Dispatch-mode skill: the per-seat breakdown from the analyzer's subagent rows - one line per dispatched agent (seat, model, tokens in/out/cache, tool calls, duration) plus the main-vs-seats share - and flag the anomalies: a seat that idles on a wait, re-dispatches, or costs more than the work it returned.
- A per-skill tool claim cites the invocation window (timestamps) the calls fall inside; a blocked Skill attempt is not a run; a Read is 'whole-file' only when its tool_input and any truncation notice say so, and 'file read N times' is not 'content re-read N times' - check the offsets.
- A skill firing late in a long session is costed at its WINDOW's ctx-per-message (its own cache-read over its own messages), never glossed with the session-wide average.
- Before reporting a skill 'never ran' or a phase 'gap', check the analyzer's companion fold (the `+N via companion loads` clause) - a reference skill loaded in service of a parent shows no row of its own BY DESIGN; the fold is the attribution, not a missing run. The dispatch-window suggestion on stampless seats is likewise citable only as inferred, never charged.
- The harness's `(Re-invocation ... previously loaded)` marker is not proof of a prior load in THIS session - claim a double-load only when the earlier invocation marker is itself in the transcript.
- A low-message loop run is judged against the skill's own STOP text in the transcript, never inferred 'incomplete' from message count.

## Guard blocks - answer the skeleton's question
The skeleton prints the per-hook table when a ledger joined and, when none did, the line *'EITHER no guard fired OR the ledger was never written - say which, do not infer'* - a QUESTION addressed to you. Resolve it from the step-3 ledger test's own output, in one of three shapes: `no guard fired this session - <docs-path>/hook-blocks/<sid>.jsonl absent and the Tools table's hook-blk column is empty`; `ledger absent - N hook-blk denial(s) in the Tools table, the hook that fired is unavailable`; or, where rows joined, one line per hook saying whether each top reason stopped honest work or caught something. A false positive is the most expensive row in that table: it costs the denial text plus the whole retried turn. Never leave the skeleton's own prompt as the answer.
- A hook-block claim names the guard whose `Blocked:` text matches; a harness-native tool error (write-before-read, disable-model-invocation refusal, input validation) is NOT a stack hook block - the hook-blk column, not the errors column, is the source.
- An uncovered ledger tail is reported with the COUNT of transcript tool calls inside it - a quiet tail (zero calls) and a real coverage gap read the same in percentages and are different facts.

## Waste analysis - checks before a row is written
The section names the specific places token use was disproportionate, each with evidence: whole-file Reads where a symbol lookup would do, the same file read more than once, oversized Bash/test output pulled into context, overlong prose in reports/summaries - ranked by tokens wasted. No row goes in before these hold:
- **A duplicate-CALL row quotes the first result's TAIL.** 'It was already in context' is a claim about the FIRST result, so read that result's end before charging the second: a truncated one - cut mid-entry, no trailing status line, short of the count the second returned - means the re-call RECOVERED data the session never had, and the waste row inverts into a correct recovery.
- **Read the ACTIVE skill's own protocol before charging a skill load or a doc read.** A load its step mandates and an orientation read its step requires are the contract's cost, not the session's waste.
- **A batch that returned nothing usable is waste too.** The shapes above are about output that was too BIG; the opposite costs the same round trips - a fan of greps that all returned '[Omitted long matching line]', a probe whose result is an error string, a re-read of a path that does not exist. Count them as dead round-trips with their share of the bill.
- **A `<persisted-output>` result is NOT in context.** When a result carries the spill marker, only the preview landed; the Read that pulls it back is a RECOVERY, and the waste is the spill, not the recovery.
- **Credit an outcome to the call that produced it.** Diff a tool_use against its own result before crediting it: a heredoc that exited 2 wrote nothing, and the file came from the Write two turns later.
- **Price the LAST message.** A run that ends on an AskUserQuestion, or on a report the user never replied to, still paid a full context re-send for it - name that message's cost in the waste section rather than closing at 'none material'.
- **Every non-zero error count gets a one-line cause.** An expected exit-1 probe and a real failure read identically in the table.
- **No cross-session superlative or comparison without the sibling's own analyzer output.** 'The best in the audited set', 'largest of the audited set', 'most blocks in the audit', 'cheaper than the sibling run' are claims about another session's numbers - load and diff that session's `--json` THIS run and cite its numbers inline, or drop the aside; real rankings route to SUMMARY.md only.
- **Elapsed time is DERIVED from timestamps, never estimated.** A gap between two runs comes from the two transcripts' own first/last stamps, stated with the locator.
- **A waste claim about reads passes four checks first:** the same file's hook-blk row (a BLOCKED read delivered zero content - it is not the waste, and its follow-up ranges are the prescribed recovery); the offsets (non-overlapping ranges are pagination, not re-reads); the content when offsets match (a same-path re-read of a GROWN file that the run then used is not a duplicate - byte-identical or nothing); and the calling skill's own contract (a read its step mandates whole is the contract's cost, not the session's waste). Truncation flips labels too: a no-offset read cut at the cap is NOT the whole file, and its ranged completion can be the larger result.
- **A 'duplicate read' claim stays inside ONE context:** a seat re-reading what the main session read is orientation across a context boundary - the seat never saw the parent's copy - and repeated Reads of the harness's `tasks/*.output` files are background-task polling; neither is waste.
- **An output-volume claim splits green from red:** a GREEN run's verbose output is waste against the summary-line recipe, a RED run's stack traces and parse errors are the diagnosis - earned cost, never a waste row.
- **Cost a failed call as what the transcript SHOWS, never as the repair you would expect:** a malformed tool call followed by a prose fallback costs one wasted call plus that fallback turn - writing it up as a 'corrected retry' invents a call that is not there.

## Protocol check - the sweeps and the table
For each skill, did the run follow its own protocol? Judge against that skill's own SKILL.md steps - for the default trio: solution-design oriented from the project docs before designing and produced an ordered minimal plan; verify-plan ran its passes against the plan rather than re-deriving it; implementer stayed inside the task contract, ran build/tests, reported per its shape. Cite turns, never assume. The check's scope is the SESSION, not the skill windows - three sweeps are mandatory before any PASS:
1. **Every stop in a flow's window** - a gate verdict counts only when an AskUserQuestion tool_use produced the answer; a free-text user reply after prose narration is the failure mode, not a held gate. Sweep 1 counts MISSING gates, not just fired ones: the analyzer emits unheld-stop candidates (a free-text user turn right after a no-tool end_turn) - check each against the active skill's stop contract before any PASS.
2. **Every `git commit` event anywhere in the session**, checked against the pre-commit checkpoint - including commits OUTSIDE any skill window, where the skips cluster. Sweep 2 classifies EVERY commit into three buckets - receipted (the gate file written), exempt-trivial (the hook's own bar: 2 files AND 15 lines, judged from the numstat), or ungated - a two-bucket sweep silently promotes exempt commits to violations or hides ungated ones; and it checks plan/cycle-note stamps before concluding a step skill 'never ran' - a resumed cycle legitimately re-runs nothing.
3. **Every user correction or redirect** - each is a first-class report item with its surrounding context, never reduced to a token-waste row. A redirect is detected from the USER's own turn text - an assistant 'good catch' with no matching user turn is not one, and injected task-notifications/system-reminders are never user corrections.

The check's SHAPE is a table, its scope the SESSION rather than the skill windows, and the three sweeps are its floor, not its whole:
- **One row per NUMBERED STEP of the audited skill, plus one per hard clause inside the steps** - `step | PASS / VIOLATED / NOT VISIBLE | the turn (timestamp) that settles it`. Open that skill's own SKILL.md and walk it; a step with no row is a step that was never checked. No PASS on the skill as a whole until every step has a row.
- **NOT VISIBLE costs a grep first.** Before marking any step unobserved, grep the transcript's raw assistant `text` blocks for it - the step may have happened in prose that carries no tool call, which no tool table can show. State the grep that came back empty.
- **Read EVERY user turn, not the ones next to command markers.** Grep every non-command, non-boilerplate user message before writing the check: a user's correction, refusal, or negative answer is a first-class report item wherever it sits.
- **A consent claim cites the ask -> mutation PAIR, by timestamp.** 'Consent-gated' means the ask came BEFORE the change it authorizes: quote the AskUserQuestion's stamp and the mutation's stamp, in that order. Aggregate tool counts prove nothing here.
- **A layer the run CHANGED is checked against the installer's contract too**, not only against the commands the model typed: what the installer promises to do to that layer, and what the end state on disk actually is. A self-corrected CLI syntax miss can sit on top of an installer that never completed the layer at all.
- **A gate claim distinguishes an existence CHECK from a WRITE:** `ls`/`test -f` output saying 'no receipt' is the receipt's absence, never its creation.
- **Compliance with a path-scoped rule is scored on an ATTACH event**, not on a read of the rule file - and the attach itself is a transcript blind spot, so in practice the honest line is 'no attach observable' and the rule is scored neither way; never convert a rule the session happened to open into evidence that its guidance was in force, and never convert the blind spot into a violation either.
- **A run whose transcript ends before its own closing artifact exists is UNVERIFIABLE, never PASS** - say which artifact is missing and what would have proved it. 'Interrupted' is anchored to the last NON-OPTIONAL step of the skill's own protocol, not to the transcript's last line: a run that finished its mandated steps and stopped before an optional one is COMPLETE.
- **A row that PRAISES a shell idiom states the observed exit status**, not the idiom's appearance: a `set -o pipefail`-less pipe, a `&&`/`||` chain or a `| head` masks the real status, so the thing that looks careful can be the thing that hid the failure.

## Efficiency verdict - what each scorecard row needs before it counts
Two authored lines, both mandatory, built from the scorecard rows: the TOKEN VERDICT (delivered / cost / avoidable share as a measured number, never an adjective - a session that spent heavily and delivered is a PASS, say so) and the EFFECTIVENESS line (did the work land, how many corrections, how many green claims had no check behind them, how many stops went unheld).

The scorecard is machine-written and every row is a measurement; a row becomes a finding only after the check beside it here has been done, and the two authored lines cite rows, never restate them.
- **Cache continuity** - a miss is counted by Claude Code's own rule (over 5% and at least 2,000 tokens re-processed against the previous request's cache). Open the turn BEFORE each listed timestamp: a system-prompt change (a rule attached, a plugin or skill loaded, a tool set that changed), an idle past the cache lifetime, or a model switch are causes that can be named. The first request after a compaction is already counted apart as an expected rebuild - never re-charge it. The re-cached tokens are the cost; the avoidable share takes only the misses whose cause a stack file owns.
- **Compaction re-reads** - a file read before a compaction and again after it is what the summary dropped, costed at the re-read's result size. Charge it to the compaction line (alfred-navigation) only when the file was in the modified set or the plan; an orientation re-read of an unrelated file is ordinary work.
- **Build-dir reads** - print the paths: a `bin/` script directory or a lockfile opened for a version pin is a legitimate read, and the row is decided by its tokens, never its count.
- **Test and build runs** - a whole-suite run at the GATE (before a commit, in a verifier's pass) is the contract's cost; a whole-suite run while iterating on one failure is the waste, costed at its result size above the summary line a scoped run returns. The green/red split from the waste checks applies: a red run's trace is earned.
- **Checked commits** - 'checked' means a test, build, lint or ci-status call sat within 40 tool calls before the commit; open that run and say whether it was green. An unchecked commit above the trivial bar is a protocol finding against the checkpoint skill's run, not a token row.
- **Green claims** - the regex reads prose; open every listed turn. A check run in an earlier turn of the same task, a dispatched seat's own run (its transcript sits in `subagents/`), or a CI status the user pasted are evidence the row cannot see - strike those before any finding, citing the turn that carried the evidence.
- **Correction streaks** - the row counts what `guard-answer-length.js` would fire on; the short-after-long count beside it says how many corrections the strict walk did not chain. Both are read, neither is a finding on its own - every user correction was already located by sweep 3, and this row is where their count meets the hook's threshold.
- **Long answers** - open the user's prompt: 'in detail', 'walk me through', 'write a plan' (in any language) lifts the cap. Count only the answers whose prompt did not.
- **Dispatch overhead** - a heavy seat spent most of its input on its own first-message context; say what it returned (the report line, the artifact) and whether a brief that returned that much needed a seat at all. A one-message seat is 100% by construction - it answered from its preload, which can be exactly right.
- **The TOKEN VERDICT's avoidable share is a SUM of costed rows that survived these checks**, with the cohort named ('~180k of 940k, 19%: two misses a rule attach caused, 18 compaction re-reads, one whole-suite run mid-iteration') - never the sum of every row as printed.

## Verdict - one table
`skill | worked as intended (y/n) | biggest strength | biggest waste source | one concrete suggestion` - one row per audited skill, each cell citing the section above that settles it.

## Every claim - citation and counting
- Diagnose an error cluster only from the quoted error text, never from counts - hook blocks carry a deterministic `Blocked:` message, a wrong-parameter error names the parameter; grep it before assigning a cause - and attribute COUNTS only after grepping every distinct signature in the cluster, never by generalizing one sampled seat.
- Prose restatements must agree with the report's own tables in the same document; derive protocol verdicts and uncosted-seat lists from the tables (set-difference), never by eyeballing; cite the value at the actual event's timestamp, not a nearby spike.
- Quote file, command, and label names VERBATIM from the tool_use input - a paraphrased label is a fabricated citation; enumerate countable events (commits, mutation probes, verbose runs) from the transcript's own output lines, never from summary memory.
- A call is credited with its EFFECT only after its own `tool_result` is read - a heredoc that errored, a write that wrote nothing, a command that exited non-zero produced no artifact, whatever the next message says.
- 'Evidence unavailable' / 'not attributable' is a CLAIM ABOUT ABSENCE and needs the grep that proves it, stated inline, before it may be written - the thing called missing is usually in the same transcript, lines away from the line that called it missing.
- Every hand count states its method inline (which stream, deduped how) so it is reproducible - the harness duplicates content into `toolUseResult` fields and a naive grep double-counts.
- A Grep result whose rows read `[Omitted long matching line]` carried NOTHING for those rows - not the field it matched, not the line - so the Read that follows it is a first read, never a redundant one; call a follow-up read redundant only after the Grep row's own text shows the value (measured: a report and its summary both called 13 four-line reads redundant on the strength of a 41-line Grep with 13 omitted rows).
- Verdict-table cells derive from THAT skill's own attributed window (its timestamps, its seats, its metric) - a run-wide total in a seat-type cell, or a row copy-pasted across skills, is a fabricated per-skill claim; print 'n/a' where the skill's contract forbids the metric.
- Every transcript measurement carries its locator - the grep/jq command and the matching line number in the bundle's own jsonl - so a checker reproduces it in one paste; and any count past a handful of events comes from a command (`grep -c`, jq), never a hand tally, with the command stated inline.
- Every rate names its denominator and cohort ('3 of the 14 main-session Reads'), never a bare percentage.
- Cite a table cell by the COLUMN it came from, verbatim. The Generated-docs table's `via Bash (r/w)` cell carries reads and writes as two numbers in one string; restating its read half as a write is a fabricated claim about what the session did - and a breach of the rule that a number a tool prints cannot be misquoted.
